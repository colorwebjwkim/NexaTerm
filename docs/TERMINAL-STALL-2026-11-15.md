# 터미널 출력 정지 조사 (2026-11-15)

사용자 증상: 메뉴와 탭은 동작하지만 터미널의 출력·입력이 멈추며, 재접속하면 회복된다. 당시 명령·통신 로그는 확보하지 않았으므로 해당 발생 건의 단일 원인으로 확정하지는 않는다.

## 재현한 결함

Rust는 화면으로 보낸 출력에 순번을 붙이고 xterm의 파싱 완료 콜백에서 `terminal_ack`를 받는다. 화면 미처리 데이터가 131072바이트 이상이면 추가 수신을 중지한다.

기존 구현에는 다음 문제가 함께 있었다.

1. ACK가 키 입력·창 크기 변경과 같은 64칸 대기열의 `try_send`를 사용했다. 가득 차면 ACK 전달이 실패하고 프런트엔드는 이 오류를 무시했다.
2. 가장 오래된 출력의 순번과 정확히 같은 ACK만 처리했다. 한 ACK가 누락되거나 나중 순번보다 늦게 도착하면 이후 ACK도 버려져 대기량이 해소되지 않았다.
3. 60초 감지 타이머를 매 루프에 새로 만들었다. 계속되는 입력·창 크기 변경으로 타이머가 재설정돼 정지 상태가 오래 유지될 수 있었다.

`terminal_output_continues_after_missing_ack`는 로컬 SSH 서버가 1MiB를 출력하게 하고 ACK 한 개를 생략한다. 수정 전에는 5초 제한에서 `terminal froze after one lost ACK`로 실패했고, 수정 후에는 전체 출력을 수신했다. 시간 제한은 정상 처리 성능 수치가 아니라 교착을 판별하기 위한 테스트 제한이다.

## 수정

- ACK를 독립적인 `watch` 채널에 누적 최고 순번으로 보관한다. 입력 대기열이 가득 차도 ACK가 누락되지 않는다.
- 완료된 순번까지 대기 출력을 누적 해제한다. 늦게 도착한 낮은 순번은 최신 완료 상태를 되돌리지 않는다.
- 정지 감지는 실제 출력 처리 진전 시각을 기준으로 한다. 처리 진전 없이 60초 동안 출력 대기량이 한도를 넘으면 해당 연결을 오류로 전환하고 대기 바이트와 재접속 안내를 표시한다.

## 배포 범위

검증: Rust 테스트 16개, clippy, fmt, 타입/Svelte 검사, 린트가 통과했다. 실제 Windows WebView E2E에서도 `terminal_ack` 한 번을 의도적으로 실패시키고 약 1MiB 출력의 끝 표시와 후속 입력 응답을 확인했다. 기존 SSH 재접속·호스트키·다중 탭·레이아웃·SFTP 전송 검증도 통과했다.

조사 중 실행 중인 앱은 `C:\Program Files\NexaTerm\nexaterm.exe`였고, 프로젝트의 release 실행 파일과 해시가 달랐다. 이 조사에서 사용자의 실행 중인 앱이나 연결을 종료하지 않는다. 프로젝트 실행 파일 빌드와 설치본 업데이트는 구분한다.
